## 1. Overview & Architecture

Kolang uses **Alembic** as the single, authoritative source of truth for relational database schema management and versioned migrations. Every database schema modification must be recorded as an auditable, version-controlled migration script within `migrations/versions/`.

### 1.1 Architectural Principles

1. **Declarative Metadata Binding:** Alembic's migration environment (`migrations/env.py`) binds directly to the centralized SQLAlchemy 2.0 `Base.metadata` defined in `packages/acp_core/db/base.py`. Any model inheriting from `Base` is automatically recognized by Alembic during schema autogeneration.
2. **Deterministic Constraint Naming:** All primary keys, foreign keys, unique constraints, check constraints, and indexes adhere to standard naming conventions (`pk_...`, `fk_...`, `uq_...`, `ck_...`, `ix_...`).
3. **Async Engine Compatibility:** Online migrations are executed asynchronously through SQLAlchemy's `async_engine_from_config` paired with `NullPool` and `asyncpg`, while safely isolating transaction boundaries.
4. **Decoupled Execution (Zero Auto-Migrate in Workers):** Application web workers (`uvicorn`) and individual HTTP request paths **never** execute migrations automatically on startup or per-request. Migrations are executed strictly as an isolated deployment or CI/CD stage.
5. **Non-Destructive Schema Evolution:** In accordance with the MVP baseline, destructive schema operations (such as dropping tables or columns containing production data) are strictly forbidden unless accompanied by a multi-phase deprecation plan.

## 2. Command Reference

### 2.1 Upgrade Commands

Apply pending schema migrations to bring the database to the desired target revision:

```bash
# Apply all pending migrations to the latest revision (Recommended)
alembic upgrade head

# Apply exactly one pending migration forward
alembic upgrade +1

# Upgrade to a specific revision ID
alembic upgrade 0001

# Apply migrations using Makefile shortcut
make migrate

# Apply migrations using standalone runner script (waits for DB readiness)
python scripts/run_migrations.py --direction upgrade --revision head
```

### 2.2 Downgrade Commands

Revert applied migrations safely in reverse chronological order:

```bash
# Revert the most recently applied migration
alembic downgrade -1

# Revert all migrations back to a completely empty schema
alembic downgrade base

# Revert to a specific revision ID
alembic downgrade 0001

# Revert using standalone runner script
python scripts/run_migrations.py --direction downgrade --revision base
```

### 2.3 Inspection & Status Commands

Inspect the active state of the database and migration history:

```bash
# Display the current revision applied to the database
alembic current

# Display full chronological history of all migration revisions
alembic history --verbose

# Display current head revisions (verifies no diverging branch heads exist)
alembic heads
```

## 3. Creating & Reviewing Migrations

### 3.1 Generating a Migration Revision

When domain models are added or modified, generate a new migration revision:

```bash
# Option A: Interactive prompt via Makefile
make migrate-new

# Option B: Autogenerate from SQLAlchemy model metadata diff
alembic revision --autogenerate -m "add_workspaces_table"

# Option C: Create an empty revision template for manual DDL
alembic revision -m "add_custom_index"
```

Migration files are stored in `migrations/versions/` with the filename format:  
`YYYY_MM_DD_HHMM-<rev_id>_<slug>.py`.

### 3.2 Pre-Commit Review Checklist

Before committing any generated migration, author must verify:

- [ ] **Review Autogenerated Operations:** Alembic autogenerate does not detect all PostgreSQL constructs (e.g. custom enum types, check constraints, or partial indexes). Review `upgrade()` and `downgrade()` line-by-line.
- [ ] **Reversibility (`downgrade()` implementation):** Every operation in `upgrade()` must have an exact inverse operation in `downgrade()`.
- [ ] **No Unintended Drops:** Check for unintended `op.drop_table(...)` or `op.drop_column(...)` caused by missing model imports in `migrations/env.py`.
- [ ] **Strict Non-Destructive Rule:** Dropping active tables or columns with persistent user data is out of scope for MVP. Deprecations must be staged across releases.
- [ ] **Deterministic Constraint Names:** Constraints must use the naming convention defined in `acp_core.db.base.NAMING_CONVENTION`.
- [ ] **Clean Git Versioning:** The migration file must be staged and committed alongside its corresponding domain models and tests.

## 4. Deployment & Startup Execution Strategy

### 4.1 Why Web Workers Do Not Auto-Migrate

In distributed and containerized deployments (Kubernetes, Docker Swarm, ECS):
- Multiple API worker processes start concurrently. If each worker attempts to execute DDL migrations on boot, database lock contention, schema deadlocks, and corrupted revision states (`alembic_version`) will occur.
- Database credentials required for DDL modifications (e.g. `CREATE TABLE`, `ALTER TABLE`) can be isolated from runtime web workers that only require DML (`SELECT`, `INSERT`, `UPDATE`, `DELETE`).

### 4.2 Standard Deployment Pipeline

Migrations must be executed in a dedicated pre-flight step before routing traffic to new API instances:

```text
┌────────────────────────┐      ┌───────────────────────────┐      ┌─────────────────────────┐
│ 1. Database Available  │ ───> │ 2. Pre-Deploy Migration   │ ───> │ 3. Start API Instances  │
│    (pg_isready check)  │      │    (scripts/run_migrations)│     │    (uvicorn workers)    │
└────────────────────────┘      └───────────────────────────┘      └─────────────────────────┘
```

#### CI/CD Pipeline (GitHub Actions)
In `.github/workflows/ci.yml`, migrations run directly against the test database before test execution:
```yaml
- name: Run database migrations
  run: alembic upgrade head
```

#### Kubernetes Deployment
Run migrations as a Kubernetes `Job` or `initContainer` before the application pods launch:
```yaml
initContainers:
  - name: db-migration
    image: kolang:latest
    command: ["python", "scripts/run_migrations.py", "--direction", "upgrade", "--revision", "head"]
    envFrom:
      - secretRef:
          name: kolang-db-credentials
```

#### Docker Compose
Run migrations explicitly or via service dependency:
```bash
docker compose -f deploy/docker-compose.yml run --rm kolang-api alembic upgrade head
```

## 5. Security & Sensitive Data Handling

1. **Zero Secret Logging:** Connection strings logged by `scripts/run_migrations.py` or Alembic CLI must redact passwords using `redact_db_url()`.
2. **Environment Variable Configuration:** The database URL is configured via `ACP_DATABASE_URL` (or `DATABASE_URL`). Raw credentials must never be committed to repository code or migration scripts.
3. **Data Migrations & Fixtures:** Migrations must never insert hardcoded production secrets, API tokens, or cryptographic keys. Default development seeds must be maintained separately in test fixtures or seed scripts.

## 6. Troubleshooting & Recovery

### 6.1 Database Connection Errors on Host
If port `5432` is occupied by another local service on your development machine, configure Docker Compose to expose PostgreSQL on port `5433`:
```bash
# In .env:
ACP_POSTGRES_PORT=5433
ACP_DATABASE_URL=postgresql+asyncpg://kolang:kolang@localhost:5433/kolang

# Then run:
alembic upgrade head
```

### 6.2 Multiple Heads Detected
If two developers create migrations simultaneously on different branches, Alembic will report `Multiple head revisions are present`. To resolve:
```bash
# Identify conflicting heads
alembic heads

# Create a merge revision linking both branches
alembic merge heads -m "merge conflicting migration heads"

# Apply merged migration
alembic upgrade head
```
